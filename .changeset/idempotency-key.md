Support an `Idempotency-Key` header on `xdr` and `func`+`auth` submissions (requires OpenZeppelin Relayer 1.9.0+). A repeated submission with the same key and request returns the transaction the first one created instead of submitting a second one, so a caller can safely resend after a lost reply. The exact signed fee bump request is stored under the key before it is sent, and every send for the key carries the same fund relayer idempotency key, so the Relayer creates at most one transaction and returns it to a resend. Once that request is stored, a send error never frees the key, since the Relayer can fail before it looks the key up or after storing the transaction; a send that gets an error, first or repeated, returns `IDEMPOTENCY_KEY_SEND_FAILED` (HTTP 503, retry with the same key, never a new one), and a repeat resends the stored transaction. Once that transaction has expired, a repeat whose resend still gets an error returns `IDEMPOTENCY_KEY_OUTCOME_UNKNOWN` with the details to check it on chain. Under a key the channel account stays locked until the transaction expires. A key reused for a different request gets `IDEMPOTENCY_KEY_REUSED` (HTTP 422), a repeat while the first request is still sending gets `IDEMPOTENCY_KEY_IN_PROGRESS` (HTTP 409), and a key whose transaction the Relayer has pruned gets `IDEMPOTENCY_KEY_OUTCOME_UNKNOWN` (HTTP 422) with the inner transaction's hash, source and sequence. A repeat of a transaction that failed on chain returns the same `ONCHAIN_FAILED` error as the first request. A transaction the fund relayer failed because it could not queue it ("Queue unavailable", no hash) now returns `TRANSACTION_NOT_SUBMITTED` (HTTP 502) instead of `ONCHAIN_FAILED`, with or without a key, and a repeat does not charge it. Keys are scoped to the caller's API key header, or to the `Authorization` header when there is none; a key sent with neither is rejected with `API_KEY_REQUIRED` (HTTP 400). Retention is set by `IDEMPOTENCY_KEY_TTL_SECONDS` (default 1 hour, minimum 5 minutes, raised to the transaction's lifetime when shorter). A transaction sent under a key is charged against the fee budget once, when it is confirmed or failed (or at send with `skipWait`), including when a repeat recovers it. Keys are 1 to 255 visible ASCII characters, since the Relayer drops other header values, and a signed `xdr` sent with a key must set `timeBounds.maxTime` (`TIMEBOUNDS_REQUIRED`, HTTP 400). The plugin client accepts `{ idempotencyKey }` on `submitTransaction` and `submitSorobanTransaction` and rejects an invalid key, and in Relayer mode takes a `pluginApiKey` to send as the caller's own plugin API key instead of the shared Relayer API key.

On the `func`+`auth` path (and unsigned `xdr`), the channel account lock is now renewed through the transaction's time bounds before every send, with or without a key, so a slow send, a lost reply or a bookkeeping failure cannot let another request reuse the channel's sequence while the transaction may still be pending. If the lock was already lost, nothing is sent and the request fails with `CHANNEL_LOCK_LOST` (HTTP 503). Acquiring a channel no longer takes the claim lock of a channel that is already locked.
